## How to run (keep accurate)
- Install with `npm --prefix backend install`; start/stop PostgreSQL on 5433 with `npm run db:up` / `npm run db:down`. Create `oda_test` once with `docker compose exec -T db createdb -U oda oda_test`; set `DATABASE_URL` to `postgresql://oda:oda@localhost:5433/oda_test?schema=public`, run `npx prisma migrate deploy` and `npx prisma generate`, then unset it. Tests refuse non-test databases; the invoice snapshot migration is applied.
- Run backend tests from `backend/` with `npm test`; frontend tests with `npm --prefix frontend test`; build with `npm --prefix frontend run build`. Focused backend suites: exports `npm test -- tests/exports.format.test.js tests/exports.api.test.js`; invoice PDF `npm test -- tests/lib/amountInWords.test.js tests/lib/shareLinks.test.js tests/lib/shareToken.test.js tests/invoiceDocument.test.js tests/invoicePdf.api.test.js`; payments, credit notes, shortage, costing and overhead tests are under `tests/`.
- Start API/UI with `npm run dev:backend` and `npm run dev:frontend`; sign in as SALESMAN to create orders at `/new-order`, review history at `/my-orders`, and view customer sales at `/my-sales`; ADMIN reviews incoming orders at `/orders` and shortages at `/shortages`; PRODUCTION can plan recipes at `/boms`, start runs at `/production/new`, and manage runs at `/production`. Run `npm run bench:play` against a fresh seeded DB (default through step 9; `-- --upto=1` through `-- --upto=9`; `API_URL` overrides); step 9 writes all report exports to `backend/exports/benchmark/`. `npm run bench:invoice-pdf` saves an invoice PDF there and prints share links. Do not reset a database unless explicitly required.
- Run staged checker from `backend/`: `npm run bench:check -- --stage=opening`; stages are `opening`, `after-purchase`, `after-issue`, `after-run`, `after-dispatch`, and `final`. Costing checks run after purchase/run; dispatch uses `after-dispatch`; payment/shortage use `final`.
- Demo password `Demo@123` works for the six seeded users; login with `POST /api/auth/login` and send `Authorization: Bearer <token>`. Master writes and invoice/order actions are ADMIN-only; customer reads are assignment-scoped for salesmen. Role and route details are listed under API endpoints.
- Sales API: SALESMAN creates orders with `POST /api/orders` (`{ clientRef?, customerId, notes?, lines: [{itemId, qty}] }`); price is server-resolved and supplied `clientRef` is idempotent. Orders are scoped for salesmen; use `GET /api/orders/:id`, `/my/customer-sales`, `/shortages`, `/:id/availability`, or `/:id/invoice-preview` per role. Approval edits require `orders:approve`; shortage uses FIFO and the active BOM.
- Invoices: create from an approved order with `POST /api/invoices`; list/detail/dispatch status are reads. Invoice lines and seller/buyer/order snapshots are immutable. Download with `GET /api/invoices/:id/pdf?disposition=attachment|inline`; request share links with `GET /api/invoices/:id/share`; public signed PDFs use `/api/public/invoices/:token/pdf`.
- Dispatch with `POST /api/dispatches` (optional partial lines); dispatch is the stock-out point. Payment APIs record linked/unallocated receipts and expose customer outstanding; date filters use inclusive IST calendar days. `GET /api/stock/finished-availability` returns reservation/free fields for non-salesmen.
- Purchases use PRODUCTION/ADMIN and decimal-string quantities/rates; adjustments use positive quantities and IN/OUT. Production runs use exactly one BOM or finished item, optional decimal-string issues, complete with actual outputs/consumption, and support overheads/variance/history under their role capabilities.
- BOM plan requires exactly one of `?batches=`, `?targetOutput=`, or `?itemId=&qty=&unit=` (max 100 batches); master writes are ADMIN, BOM writes ADMIN/PRODUCTION. Prisma commands from `backend/`: `npx prisma format`, `npx prisma validate`, `npx prisma migrate dev`, `npx prisma migrate status`.
- Seed with `npm run seed`; `npm run seed:reset` is destructive and refuses production; `npm run balances` prints ledger balances. Numbering uses `nextNumber(tx, 'INV', date)` inside the transaction. Audit reads require ADMIN/ACCOUNTANT/OWNER; `rg -n "parseFloat|toFixed" src/lib` should return no matches.
- Stock append-only trigger check: `docker compose exec -it db psql -U oda -d oda`, then `UPDATE "StockMovement" SET "qtyChange" = 1;` must fail. Copy `backend/.env.example` to `backend/.env` and set a private JWT secret before use.

## Frontend structure
`src/app/registry.js` owns the page registry; add new page imports and `registerRoute` calls only after its marked append-only comment. Route definitions declare path, component, allowed roles, title, optional navigation metadata and home roles. `App.jsx` builds guarded routes from this registry; `AppShell` renders salesman mobile tabs or the staff sidebar. Tests use the mock Axios adapter and provider wrappers; no data-fetching library is used.

## Frontend pages
- `/` redirects authenticated users to their role home; anonymous users go to `/login` (`src/App.jsx`).
- `/home` is available to all five roles (`src/pages/HomePage.jsx`); navigation cards come from registered pages.
- `/login` is public; redirects signed-in users to an allowed requested page or their registered home (`src/pages/LoginPage.jsx`).
- `/new-order` is SALESMAN-only; loads assigned customers, backend-priced finished goods and finished availability, and queues failed network submissions (`src/pages/salesman/NewOrderPage.jsx`).
- `/my-orders` and `/my-orders/:id` are SALESMAN-only order list and detail pages; `/my-sales` shows customer-wise sales (`src/pages/salesman/MyOrdersPage.jsx`, `src/pages/salesman/MyOrderDetailPage.jsx`, `src/pages/salesman/MySalesPage.jsx`).
- `/orders` is ADMIN/OWNER/ACCOUNTANT inbox; `/orders/:id` is order detail, editable only for ADMIN on SUBMITTED orders; `/shortages` is ADMIN/OWNER-only (`src/pages/admin/orders/OrdersInboxPage.jsx`, `src/pages/admin/orders/OrderDetailPage.jsx`, `src/pages/admin/orders/ShortagesPage.jsx`).

## Decisions (deviations from AI_CONTEXT.md and why)
- Step 52 variance previews use integer base quantities and the server's basis-point threshold/rounding; saved runs show the server variance response. PRODUCTION cannot read costing, so the cost sheet is not requested or shown for that role.
- Step 51 downloads PDFs as authenticated blobs and uses the filename from `Content-Disposition` (invoice number fallback); WhatsApp opens the server-generated URL and does not send a message. Payments cannot exceed the invoice due.
- Step 50 stock cover comes from `GET /api/orders/:id/availability`, not client-side stock calculations; ADMIN approval above free stock is refused by the backend and the UI offers the free-stock quantity. The real backend returns 409 `INSUFFICIENT_STOCK` (not the prompt's 422), and availability/shortage reads are restricted to ADMIN/OWNER.
- Step 48 offline submissions use localStorage key `oda.orderQueue` with backend-compatible idempotent `clientRef`; the page still requires connectivity to load customers/catalog, and no service worker/PWA is included. Order pricing uses the real `/catalog/order-items?customerId=` endpoint, which resolves customer prices before defaults. SALESMAN finished availability returns `availablePackets` without `freePackets`; the UI uses that actual field and does not request stock summary. The order total is taxable-only; GST is added at invoice time.
- Step 49 order history refreshes manually and every 60 seconds only while the tab is visible; browser push notifications are not included. Sales totals are summed with integer paise arithmetic from the customer-wise API rows.
- Step 47 demo accounts are intentionally shown to evaluators and controlled by `VITE_SHOW_DEMO_LOGINS`; login redirects only to a registered route allowed for the authenticated role.
- Frontend step 46 uses localStorage key `oda.session`, refreshes stored users through `/auth/me`, and uses `useAsync` rather than a data library. `/status` remains public; the registry is append-only, with Home registered for all roles. `@testing-library/jest-dom` is pinned to v6 because v8 requires Vitest 5 and conflicts with the required Vitest 2.1.9.
- DB host port is 5433 because the Windows PostgreSQL service occupies 5432
- No round-off line; GST is computed per invoice line and then summed.
- Invoice snapshots are stored in `Invoice.snapshot`; database triggers prevent invoice/line deletion and line updates. Invoice cancellation may change only status, cancelledAt, and cancelReason, and only once. Step 45 uses stored seller/buyer snapshots and line amounts; no global auth middleware exists in `app.js`, so public PDF routing is mounted before per-route-auth invoice routes. Phone and display unit have no invoice snapshot columns and use current masters.
- Authentication reloads account/role on every request, so deactivation, deletion and role changes take effect immediately. Failed-login audits store attempted email, never password; unknown emails have null userId; audit date bounds are inclusive and limit is capped at 100.
- Opening stock movements use item id as `sourceId` because there is no opening-document model. Financial-year ranges start at inclusive IST midnight and end at exclusive next-year IST midnight.
- BOM cloning supports pack-size variants by retaining raw lines and replacing packaging for a new SKU; source remains unchanged. Planned consumption rounds fractional batches to four decimals and output/material base quantities half-up to integers.
- Run-line `issuedQty` is total stock-out (consumed plus scrap); step 17 starts raw issues and packaging may issue at completion. Variance compares total issued to plan using saved tolerance and strict `abs(bp) > tolerance`; cartons -10% flag, pouches -3% do not at 300 bp, extra flags to explain in README.
- Production run date filters inclusively use `startedAt`; cancellation reverses issues as positive `ADJUSTMENT` rows and retains history. Benchmark playback uses public APIs and `after-run`; tests reuse `prisma/seed.js` and bcrypt cost 4.
- Customer prices override defaults only when positive integer paise; omit items without a positive resolved price. Orders snapshot server-resolved prices and integer packet quantities; repeated same-salesman clientRef is the offline-sync idempotency contract.
- Order/customer-sales dates are inclusive IST calendar days (`to` uses exclusive next day). Reservations count effective APPROVED/INVOICED quantity less dispatched; other statuses do not reserve. Preserve legacy `availablePackets`; reserved/free fields are non-SALESMAN only.
- Order approval blocks shortages without force but permits covered partial quantities; manual cancel is only SUBMITTED/APPROVED, later cancellation uses credit notes. Invoice GST rounds per line then sums components; no round-off line.
- Sales reduce finished stock only on dispatch through `ledgerService.addMovement`; DISPATCH has no rate because run stores production cost. Dispatch locks invoice/items, checks free stock after other reservations, and never edits invoice quantities; order becomes DISPATCHED only when fully sent.
- Customer balance is `max(0, posted invoice totals - all payments)` with negative difference as credit; reject overpayment and disallow advances, though unallocated payments reduce total outstanding. Payments linked to later-cancelled invoices remain paid and become unallocated credit; v1 has no payment edits/deletes/reversals.
- Ageing uses whole IST days from issueDate without credit terms; as-of includes eligible invoices/payments through that day and applies unallocated funds oldest-first. Invoice cancellation creates one credit note, changes only status/cancellation fields, cancels order and appends positive SALES_RETURN for assumed returned/saleable goods; unique orderId prevents reinvoicing. Step 39 GST nets credits.
- Step 32 read-only audit: full approval beyond free stock is rejected by Step 26 as HTTP 409 `INSUFFICIENT_STOCK` (not the prompt's 422), with `availability` details including line `shortBy`; do not change this established behavior. Reduced `approvedQty` is allowed if covered and an admin can reject with a reason. Invoice creation copies the GST draft: seller state 33 and Distributor B state 29 produce `isInterState: true`, place of supply 29, IGST only; Retailer A state 33 remains CGST/SGST.
- Submitted finished-goods orders compete for free inventory FIFO; approved/invoiced quantities are reserved. A shortage is addressed by approving a reduced quantity, rejecting, waiting for production, or creating a new backorder order. Suggested batches use the highest-version active BOM. The adjustment API's real reason enum uses `OTHER`; explanatory text is submitted as `note`.
- Step 33 confirms the seeded benchmark uses public endpoints for order, invoice, dispatch, shortage, and payment; the full Distributor B order remains SUBMITTED, and the checker uses `after-dispatch` and `final` (not separate invoice/shortage/payment stage names). Existing Vitest `fileParallelism: false` protects the shared `oda_test` DB, so its config was unchanged.
- Weighted average is receipt valuePaise / positive base quantity rounded to six stored decimals; `getAverageRate` retains unrounded Decimal behavior. FINISHED rates are opening-only; PRODUCTION_OUTPUT is excluded from material averages.
- Overheads belong entirely to their run; per-good-packet cost `(material + overhead) / actualGoodQty` rounds half-up to four decimals; scrap is costed but excluded from divisor. Overhead changes make no ledger movement and are audited. Overhead reads use `production:read` (PRODUCTION/ADMIN/ACCOUNTANT/OWNER); costing remains ADMIN/ACCOUNTANT/OWNER.
- Cost sheet variances use saved line rates; never-issued components use as-of weighted rate only for planned cost. Product averages divide total material+overhead by good quantity; margin uses Item.sellingPricePaise, not customer prices.
- Reports follow reportKit sections; sales-register status groupBy totals ignore pagination. Immutable posted issueDate means boundary fixtures insert directly in test DB. Step 36 distributor helper was invalid; Step 37 used public APIs without modifying it.
- Step 44 followed explicit export/product-costing scope over stale Next Step: paise exports as two-decimal rupees, PDF omits `Rs` for Helvetica glyph limits, CSV selects one section, exports are read-only/unaudited. Step 45 prints `Rs ` with Helvetica, uses seven-day HS256 links, and prefers PUBLIC_BASE_URL to request host.
- Customer/product reports include POSTED invoices and filtered-total shares (basis points may not sum to 10000); item names/HSN use line snapshots, earliest differing snapshot wins; later-period credits do not restate earlier sales, while GST nets credits in its period.
- GST summary includes all invoice statuses by issueDate and credits by createdAt; GSTR-3B/HSN net full line values. B2CL is unregistered inter-state total >25000000 paise; UQC map: packet/PAC, pcs/PCS, g/GMS, kg/KGS, ml/MLT, l/LTR, unknown/NOS. Cancellation count is zero because cancellations use credit notes.
- Stock movement classification uses this table; unknown type/sign combinations fall back to sign classification and are counted as unclassified:

  | Movement types | Summary columns |
  | --- | --- |
  | OPENING, PURCHASE, PRODUCTION_OUTPUT, SALES_RETURN | openingEntries, purchases, productionIn, returnsIn |
  | PRODUCTION_ISSUE, PRODUCTION_SCRAP, DISPATCH | productionOut, scrapOut, dispatchOut |
  | ADJUSTMENT (positive / zero or negative) | adjustmentsIn / adjustmentsOut |

  Stock reconciliation is shown per item. Stock summary excludes finished-goods valuation; use production costing for that. Stock ledger reads are capped at 20000 movements.
- Purchase-register amounts are shown as entered without GST calculation; input tax credit is not tracked in v1. Production reports use saved run/line variance flags, rates and costs; period uses completedAt or startedAt, and consumption follows paginated runs.
- Report exports do not bundle sections into ZIP; XLSX dates are text and each CSV download selects one section.

## Assumptions (copy into README at the end)
- The `last7` date preset includes today and the previous six IST calendar days; `thisFY` runs from the current FY start through today.
- Project source/guidance live at the Git repository root; `sumInvoice(lines)` expects `taxablePaise`, `gstRateBp`, and `interState`.
- Opening finished goods are valued at Rs 30/packet (3000 paise), as the brief provides no cost; `seed:reset` preserves Prisma's `_prisma_migrations` table while truncating application tables.
- Purchase request quantities and rupee rates are decimal strings, keeping input conversion independent of binary floating-point.
- Customer price PUT accepts `{ prices: [...] }` and upserts only the submitted item prices.
- BOM PUT preserves notes when omitted; clone copies source notes and line overrides apply only to items present after replacements. Plan requires exactly one mode; issued quantities use the selected BOM item's dimension and convert to base units.
- The main benchmark intentionally leaves Distributor B's shortage order unapproved; a backorder is a new order after production replenishes stock.
- Receivables ageing includes customers with an eligible invoice and an outstanding balance or remaining credit; `detail=true` opts into invoice rows, and sections are capped at 50000 rows. Invoice PDFs use current customer phone and item display unit because the schema has no historical fields for them.
